Redmine backup plan

This is the current scope of the native Ruby implementation. Installation/configuration instructions are in INSTALLATION.md and CONFIGURATION.md; the provider catalog is in STORAGE.md. The earlier Python/rclone/timer/Apps Script prototypes are superseded and are not part of this project.

Policy

Item Policy
Database Full PostgreSQL backup every day
Application/files Full backup every day, with no incremental dependency chains
Schedule Configurable time and timezone; default 20:00 Asia/Kolkata
Availability Redmine stays online during capture
Local retention Configurable successful dates; default 3
Remote retention Configurable successful dates per destination; default 10, with per-target override

Recovery coverage

Each recovery point includes the full Redmine database, application source/customizations, plugins, themes, assets, dependency lockfiles, snapshot-referenced attachments, required external configuration/environment files, Rails key material, SMTP state/secrets and Redmine service definitions. Configured provider SSH key/known-host files and PostgreSQL TLS files are included when applicable/readable.

Automatic discovery is supplemented by explicit additional paths. Newly discovered coverage is flagged. Missing required paths fail capture rather than being silently omitted. Gateway applications/settings/services, Let’s Encrypt material, disposable logs/caches and the local backup store itself are excluded.

A manifest records runtime versions, source/archive mappings, captured files, artifact sizes and SHA256 hashes. A private bootstrap preserves effective settings, required key/configuration material, grants and plugin control history for offline recovery. No completed historical backup directories are recursively included in a new backup.

Scheduling and execution

The native worker evaluates a durable schedule/queue. A missed schedule after an outage triggers one fresh current backup once the app/database/worker are ready. It does not invent historical recovery points for every missed day. Explicit Pause is respected; manually requested work does not suppress the next scheduled slot.

A process lock prevents concurrent writers across startup hooks/workers/admin clicks. Heartbeats show liveness; durable state identifies interrupted work. Incomplete capture is restarted; valid captured payloads can proceed to packaging/upload retry. A still-running hung process is not automatically overtaken by another writer.

Capture uses an exported PostgreSQL repeatable-read, read-only snapshot for the dump and referenced-attachment inventory. Attachment data is checked for size and available stored digest while copying; archive components receive SHA256 checksums. Streaming, disk reserve checks, process timeouts and worker CPU/I/O priority limit impact. The snapshot does not claim an atomic whole-filesystem image.

Packaging and upload

Separate components are the default. Single-ZIP mode wraps the same dump/archive/bootstrap/manifest/guide and checks the resulting archive. Already compressed components are stored without recompression. Packaging retry reuses verified components; upload retry reuses verified payloads without another dump.

Adapters cover Google My Drive/Shared Drives, OneDrive Personal/Business, SharePoint document libraries, SFTP and S3-compatible endpoints. Authentication choices and provider prerequisites are indexed in provider authentication. Other Ruby-capable services are cataloged as future adapters, not implied implemented support. Authentication, resumability, integrity checks and ownership-scoped retention are provider-specific. A completion marker is published only after all required artifacts verify.

The optional secondary supports:

  • Disabled: primary verification is sufficient; secondary fields, checks, uploads and alerts are not required.

  • Redundant: attempt both copies every run, even after primary failure; both must verify. One success is Partially Protected and pending local artifacts stay protected.

  • Failover: exhaust primary upload retries, then use the same payload at secondary. Report Failover Used, alert on primary failure, and try primary first on the next run.

Each destination has separate credentials, sessions, completion status and retention. Historical retries retain their original target identity; changing targets cannot silently redirect old jobs or delete a different namespace.

Retention and provider protection

Counts are distinct successful backup dates, not wall-clock age. Zero, negative, fractional and malformed retention inputs are rejected. Pending/unuploaded local sets and the last good recovery point are protected even if limits are exceeded.

Provider versioning and immutable retention locks are separate opt-in capabilities. The initial implementation checks existing S3 versioning/Object Lock support and verifies requested object protection. It does not enable irreversible bucket-wide policies or broaden credentials. Unsupported/failed protection is reported separately.

Locked cleanup is deferred without invalidating a verified upload. Retention can exceed configured counts while locks apply. Old versions, provider recycle bins, duplicate markers and orphaned partials can consume additional storage. Cleanup never blindly sweeps a bucket/folder or bypasses a hold.

Alerts, visibility and recovery

Alerts use the existing Redmine mailer and simple HTML/plain-text templates. Existing users/groups resolve to active deduplicated recipients. Failure notifications use bounded retry and per-recipient delivery tracking. Test Notification is available; recovery confirmations and scheduled daily-success notifications are optional/off by default.

The dashboard separates capture/packaging, primary/secondary upload verification, requested protection and cleanup. It shows safe failure codes, heartbeat, coverage changes, audit history and setup checks. Selecting an alert recipient grants no backup-administration privilege. Native alerts cannot be sent while the server/worker itself is down.

The offline verifier and bootstrap helper work without the original Redmine database. Recovery Mode blocks scheduling, cleanup/uploads and operational notifications on a restored/test instance until deliberate activation. The restored schedule remains paused. A recovery drill must also verify the separately provisioned gateway/HTTPS infrastructure.

Acceptance

Validate administrator access, settings persistence, configurable retention, both secondary modes, scheduling/catch-up, lock exclusion, encrypted state, interrupted upload/packaging retry, integrity checks, ownership-safe cleanup/lock deferral, existing mail delivery, actual PostgreSQL capture and attachment recovery. Unit/isolated integration checks are documented in VALIDATION.md. A chosen-provider live upload and full restore drill remain separate operational validations.

Manually pinned recovery points and more proactive storage/credential-expiry warnings remain optional future enhancements. Current implemented boundaries are recorded in IMPLEMENTATION.md.

Installation

Use a staging Redmine first. This repository does not deploy itself.

The hosted reference and offline documentation/index.html are generated from the same repository documentation. Keep all procedure changes here.

  1. Check Redmine 7.x, its Ruby/Rails versions, PostgreSQL, free space and the existing lockfile. Preserve the working Redmine installation using your existing operational procedure.

  2. Clone this repository into REDMINE_ROOT/plugins/redmine_backup_plugin. The repository basename may differ; the plugin explicitly registers its actual directory.

  3. As the Redmine service account, run bundle install from REDMINE_ROOT. Inspect the dependency changes; do not automatically upgrade unrelated Redmine gems. S3 and SFTP require their declared gems; ZIP and PostgreSQL must match Redmine’s current lockfile.

  4. No plugin table migrations are needed. Restart the Redmine web service so the routes, menu and mailer are loaded.

  5. Open Administration → Backups. Choose the local directory before creating the first backup. It defaults to a private redmine-backups subdirectory of Attachment.storage_path. Its existing parent must be writable, persistent and non-public.

  6. Configure provider settings, retention and alert recipients. Add any external Redmine paths the discovery preview cannot identify. For Google Drive/OneDrive, register the exact displayed callback and use Save settings and connect storage account; follow provider authentication. Installation alone does not authorize a storage account.

  7. Configure the native worker as a supervised process. Copy the template only after replacing its absolute paths/service user and adding the same environment files used by the web service. Do not run the worker as root.

  8. Confirm the heartbeat and path checks. Queue a test notification and a manual backup. Check capture, every required destination, integrity verification and cleanup status independently.

  9. Perform the documented isolated restore drill, then enable the schedule. The initial implementation is not production-validated merely because unit tests pass.

Worker systemd example

Example install commands (replace paths, service names and account for the actual host):

cd /path/to/redmine/plugins
git clone https://github.com/KrishnaST/redmine-backup-plugin.git redmine_backup_plugin
cd /path/to/redmine
bundle install
sudo systemctl restart redmine.service

Copy plugins/redmine_backup_plugin/templates/redmine-backup-worker.service to /etc/systemd/system/redmine-backup-worker.service, edit it as described below, then run the service commands. The worker must share the web service’s Rails key, environment and account; a clone and web restart alone do not start scheduled backups.

Edit templates/redmine-backup-worker.service for the actual service account, Redmine root and absolute Bundler executable. Include the environment/secret inputs required by Redmine and its SMTP delivery plugin. OS service configuration is installation infrastructure; daily operation and backup policy are administered in Redmine.

sudo systemctl daemon-reload
sudo systemctl enable --now redmine-backup-worker.service
sudo systemctl status redmine-backup-worker.service

The worker evaluates the schedule every 15 seconds and writes a heartbeat during long operations. It uses a filesystem process lock, not a lease that lets a second writer overtake a still-running job. A crashed process releases the kernel lock; durable job state guides recovery. A hung process requires supervisor/operator intervention.

Local directory migration

The directory is editable through the UI before there are queued jobs or backup records. Existing data is not moved automatically. For an existing installation, pause scheduling, stop the worker and web writes, copy the entire private directory preserving ownership/modes to the reviewed destination, update the plugin’s non-secret local_directory setting through a controlled Rails maintenance session, then restart and validate history/keys/paths. Keep the original until validation succeeds. Do not point a new empty state directory at an existing remote namespace.

Uninstall

Pause scheduling, stop/disable the backup worker and remove the plugin directory using the normal Redmine maintenance procedure. Preserve the private backup state, recovery keys and remote backups deliberately; uninstall does not automatically delete them. No database tables are dropped. The Redmine plugin settings entry can be removed through an explicitly authorized maintenance action if desired.

Configuration and storage

All routine settings are on Administration → Backups. Secret inputs are write-only: blank preserves the stored value. Non-secret settings use Redmine’s plugin Setting entry. Credentials, refresh grants, upload sessions, audit and queue state are encrypted in a private filesystem directory using a key derived from the existing Rails secret.

Retention

Field Default Meaning
Local successful dates to keep 3 Keep the newest verified local capture for each retained successful date
Default remote successful dates to keep 10 Default for each destination independently
Destination remote dates to keep Blank Override the remote default for that specific destination

Each count accepts an integer from 1 to 3650. Zero, negative, fractional and malformed values are rejected. Counts represent distinct successful backup dates, not a wall-clock expiry. Multiple successes on one date do not each consume a date slot. Changes take effect during the next successful upload/retention pass, not immediately on Save.

Retention protects unuploaded local sets, local sets awaiting a required redundant copy, the latest local capture, and the last recognized complete remote point. Limits can be exceeded while uploads/locks are pending. Deleting one remote set never means deleting unrelated directories or another destination. Provider versions, deleted-file bins and duplicate markers may consume additional remote storage outside the visible successful-date count.

Secondary destination

Disabled by default: no secondary settings/checks/uploads/alerts are required. When enabled choose:

  • Redundant: attempt both destinations on every run, including when primary fails. Both verified copies satisfy protection. One verified copy is Partially Protected; its local payload remains protected for retry.

  • Failover: exhaust bounded primary upload retries, then upload to secondary using the same artifacts. Next run tries primary first. A valid fallback gives Failover Used status while the primary failure generates an alert.

An upload retry skips already verified targets. Deliberate primary backfill of a failover set is supported while its local artifacts remain available. Changing provider/destination does not redirect historical retries: each run retains its original configuration. Remote cleanup is skipped when the current destination identity differs from that historical target.

Google Drive

Register a Web OAuth client with the callback shown below. Enter client ID and Web client secret, then click Save settings and connect storage account. Leave folder ID blank to create an application-owned Redmine Backups folder after consent. Scope is drive.file with offline authorization; it grants access to files created/authorized for this application, not unrestricted Drive access. An existing folder must be explicitly accessible to this application; entering its ID alone does not grant access. See provider authentication for setup and supported mechanisms.

The adapter uses resumable upload sessions. Shared Drive authorization and tenant-specific behavior require a live compatibility test; do not assume consumer Drive behavior proves Shared Drive support. Reconnect through the same slot if an expired/revoked grant prevents refresh.

OneDrive and SharePoint

Register a Microsoft Entra HTTPS Web application with delegated Files.ReadWrite and offline access. Enter client ID, tenant ID (blank means organizations) and Web client secret. Click Save settings and connect storage account for browser sign-in with S256 PKCE. Leave folder ID blank to create Redmine Backups after consent. Microsoft consumer accounts may need consumers or common and a matching registration audience.

Choose OneDrive Personal, OneDrive for Business or SharePoint document library explicitly. Personal uses the consumers audience. Business/SharePoint support delegated and application identities; configure a drive or site ID for application access. A site selects its default library; drive ID selects a particular library and takes precedence. See all authentication methods. Upload sessions and preauthenticated downloads are stored privately; Graph bearer tokens are not forwarded to signed download hosts.

For both OAuth providers register exactly:

https://YOUR-REDMINE-HOST[/relative-root]/admin/backups/oauth/callback

The callback is derived from Redmine’s HTTPS host and relative-root settings. OAuth state is one-use, time-limited and bound to the selected destination. These upload registrations are separate from any SMTP OAuth application.

SFTP

Configure host, SSH port, username, existing remote directory and a local known_hosts file. Select SSH private key (readable private-key path and optional key passphrase) or SSH password. Only the selected method’s fields are enabled. Host-key verification is mandatory; populate and verify known_hosts independently. The plugin does not trust keys on first use, create remote directory trees or run remote shell commands. Existing partial bytes are compared with the local source before offset resume; final verification uses streamed read-back.

S3 compatible

Configure bucket, region and optional key prefix. Leave endpoint blank for AWS; R2/B2 require the provider’s HTTPS endpoint. Select the IAM role/default SDK credential chain, access keys, or temporary STS credentials. Static key fields are hidden for the default chain; the session-token field appears only for STS. Only the installation-owned namespace is managed. Multipart sessions are checkpointed; multipart ETags are not treated as MD5 checksums. Verification reads back the actual bytes.

Require versioning checks that bucket versioning already exists. Require retention lock additionally checks pre-enabled Object Lock and requests a COMPLIANCE retain-until period. These are opt-in per destination; the plugin never enables bucket-wide irreversible policies. Verify that the intended lock period and cost are acceptable before use. Protected uploads are checked again through object metadata.

Locked cleanup shows Deferred Locked. It does not invalidate a verified upload. Noncurrent versions and deleted-marker history may remain subject to provider lifecycle policies. S3-compatible endpoints do not automatically support AWS’s versioning/Object Lock APIs; capability failures are reported.

Retry and history

The Show backup status on administrator homepage option is on by default. The homepage panel shows the latest result, last verified local/remote success, worker heartbeat, schedule and recovery mode. It does not expose paths, credentials or backup controls to bank/non-administrator users. Scheduling remains disabled until explicitly enabled.

Back Up Now, Retry Upload, Retry Packaging and Test Notification enqueue durable work. The browser does not perform long-running capture or transfer. History separates local capture, packaging, primary/secondary verification, requested protection and cleanup. Retry Packaging checks the preserved manifest/components before creating a new wrapper. No bandwidth throttle is configured, but provider Retry-After/backoff remains in effect.

Check Setup queues tool/path/disk/provider capability checks and shows their results on the dashboard. Backup/upload failures always generate a deduplicated notification request. Recovery confirmations and scheduled daily-success summaries are optional/off by default. Emails include the run/event, timestamp, last local/remote success and one administrator details link. Recipient selection is resolved against active current users/group members at delivery time.

Google setup

  1. Enable the Drive API in the Google Cloud project.

  2. For personal/Workspace browser login, create a Web application OAuth client and register exactly the callback shown in Redmine. Configure consent-screen audience/test users and review Google’s Testing-mode refresh-token lifetime restrictions. Select Browser sign-in, enter the client ID/secret and Save settings and connect storage account.

  3. The scope is https://www.googleapis.com/auth/drive.file with offline access. Leave folder ID blank to create an application-accessible Redmine Backups folder. An arbitrary preexisting folder ID does not itself authorize the application to use that folder.

  4. For a service account, paste its private JSON in the write-only field and add that identity to the intended Shared Drive. Supply the Shared Drive ID to create Redmine Backups there, or an existing folder ID within it. Requests use Shared Drive API flags and folder checks. Service accounts cannot own personal My Drive files and have no personal storage quota.

  5. For Workspace domain-wide delegation, authorize the service account’s client ID and Drive scope in Workspace administration and enter the exact user to impersonate. The signed assertion contains that user as its subject. This does not impersonate personal Gmail accounts.

  6. Connect, Check setup, perform a real upload/read-back and restore drill before relying on scheduled protection.

Microsoft setup

  1. Register an Entra application with the audience appropriate to the account. Personal OneDrive uses consumers; business browser/device flows default to organizations. App-only client-credential flows require a specific tenant GUID or verified tenant domain.

  2. For browser sign-in, register exactly the displayed HTTPS Web callback and configure delegated Files.ReadWrite for OneDrive or Files.ReadWrite.All for SharePoint, with offline access. Enter the confidential Web secret where required.

  3. For device code, enable public-client flows in that registration. Save and connect, open the Microsoft verification link, enter the displayed user code, approve access and select Complete sign-in. The browser does not receive the private device code; it stays encrypted in control storage. Polling observes provider intervals, slow_down, expiry and settings/user binding. Resume Microsoft device sign-in on the dashboard returns to an unfinished flow. A completed grant and created folder remain encrypted if the worker is busy, so retrying does not repeat authorization or folder creation.

  4. For application identities, grant suitable Microsoft Graph application permissions and administrator consent. Prefer narrowly scoped site grants where supported by the required APIs. Upload, listing, read-back and deletion/retention all need access; a read-only grant is insufficient. Application permissions do not grant access to personal consumer OneDrive.

  5. Client secret mode exchanges the confidential app secret. Certificate mode signs short-lived PS256 assertions with a SHA256 certificate thumbprint; upload the matching public certificate in Entra. Private keys must be RSA, at least 2048 bits, and match a currently valid certificate.

  6. Workload identity reads a fresh OIDC assertion from the configured private file on each renewal. Provision matching issuer, subject and audience in Entra. The platform, rather than the plugin, issues/rotates those assertions.

  7. Managed identity works on Azure VM IMDS and Azure App Service identity endpoints. The platform must provision the identity and Graph permissions. No configurable arbitrary token endpoint is exposed. Metadata requests bypass HTTP proxies, remain on loopback/link-local HTTP endpoints, use required platform headers and never follow redirects.

  8. For On-Behalf-Of, an upstream service must supply and renew a user access token whose audience is this application. ID tokens, app-only tokens and arbitrary Graph tokens are not interchangeable with that assertion. The plugin cannot manufacture a continuing upstream user session.

  9. ROPC is explicitly a legacy option. It cannot complete MFA/passwordless login and fails under incompatible Conditional Access/federation policies. Do not weaken tenant policy merely to use this mode. Passwords are encrypted and never rendered back.

SharePoint and business drive addressing

Choose SharePoint document library for library storage. Enter a drive ID to select a particular document library, or a SharePoint site ID to address its default library. Drive ID takes precedence. In business delegated mode, leaving both blank uses the signed-in user’s drive. Application-only modes and SharePoint require one of these explicit destinations; they never call /me.

Typical discovery endpoints, using an appropriately authorized Graph tool, are GET /sites/{hostname}:/{site-path} followed by GET /sites/{site-id}/drives. These identify site/library IDs; they do not grant access. Folder ID refers to a folder inside the selected drive, not a site or library ID. Leave it blank to create Redmine Backups after authorization.

Folder health checks validate accessibility and type. Retention checks the configured parent folder and, when a drive ID is configured, its drive ID. Historical retries keep their captured destination; switching drives does not redirect deletion into another library.

Callback, credentials and external identity files

Browser OAuth registrations must use the exact displayed HTTPS URL:

https://YOUR-REDMINE-HOST[/relative-root]/admin/backups/oauth/callback

Callback state is one-use, time-limited and administrator/session/settings bound. Storage registrations are independent of SMTP OAuth. Blank credential inputs preserve existing encrypted values; changing authentication identity invalidates the old cached access/refresh grant. Tokens, passwords, service-account JSON and certificate/private-key inputs never appear in public plugin settings or rendered form values.

Workload/OBO assertion files must be readable by the worker, private on Linux (no group/other permissions), bounded in size and rotated by their owning platform/service. They are ephemeral credentials, not a portable identity system: re-provision their issuer/rotation after disaster recovery. They are not automatically added as durable archive sources; add only appropriate long-lived deployment configuration to additional backup paths. Embedded private key/secret configuration is already in the private recovery bootstrap.

Azure App Service supplies IDENTITY_ENDPOINT and IDENTITY_HEADER; do not manually fill these on a non-Azure host. For Azure VM identities, the fixed IMDS endpoint is used. These variables must be available consistently to the web service (Connect) and supervised worker (renewal).

Flows that do not fit this web backup application

  • Google device authorization is for TVs/limited-input devices with the corresponding client type; Google’s policy requires using a client appropriate to the platform. Redmine is a web application, so a misleading Google device-login button is not provided.

  • Desktop/native loopback redirects are for native clients, not this remotely hosted HTTPS web callback.

  • Implicit/browser-only token acquisition has no unattended refresh grant. Externally obtained access tokens can be imported explicitly with expiry; the plugin does not expose tokens in a URL fragment or pretend they provide permanent backup authorization.

  • OAuth refresh tokens and PKCE are renewal/security mechanisms, not additional account types. Personal Google Drive is already covered by user OAuth.

Troubleshooting

A successful connection queues a new setup health check. Refresh the dashboard after the worker processes it. Saving configuration invalidates previous setup results; a warning from before authorization does not describe the newly saved grant. The supervised worker refreshes Redmine’s settings cache on every runtime load, keeping public destination IDs and private credentials in sync. A cloud check cannot pass without a destination folder.

  • Callback mismatch: copy the exact Redmine callback, not the GitHub Pages documentation URL.

  • Invalid client: check app audience, client ID, secret expiry, certificate registration or federated trust.

  • Missing refresh grant: reconnect with offline consent using a matching client type.

  • Google folder returns PROVIDER_HTTP_404: the folder ID is wrong, deleted, or inaccessible to this application. Successful account consent alone does not grant access to an arbitrary folder under drive.file. Use the application-created Redmine Backups folder; alternatively clear the folder field and reconnect to create one. Do not broaden permissions or silently switch the destination for historical upload retries. After correcting settings, run Check setup and validate a new backup.

  • Device flow pending: finish Microsoft sign-in and wait for the displayed polling interval; expired/denied codes require a new flow.

  • Shared Drive quota/folder errors: use a team-owned folder for a service account, or delegate to an authorized Workspace user.

  • Graph app-only errors: supply the correct tenant and drive/site ID; verify Graph permissions and actual site grants for every required operation.

  • Managed identity unavailable: verify Azure hosting/identity configuration; an ordinary client ID on a non-Azure server is insufficient.

  • WORKER BUSY RETRY SETTINGS: let the active backup finish, then retry; a completed device grant remains private until its pending flow expires.

Redmine recovery guide

This guide is included in every backup. Test it on an isolated replacement host before relying on a backup. Recovery is an administrator operation, not an automatic production restore.

1. Select and verify

Choose a complete verified recovery set. Download all components, or the single ZIP. If using ZIP, unpack into a new private staging directory after checking that entry names contain no absolute paths or parent traversal. The ZIP contains manifest.json, database.dump, application.tar.gz, bootstrap.json and this guide. Separate mode provides the same files directly.

Run the repository’s standalone verifier with Ruby:

ruby bin/redmine-backup-verify /private/staging/manifest.json
pg_restore --list /private/staging/database.dump >/dev/null

The verifier checks file sizes and SHA256 against the manifest. The dump catalog check does not prove successful restore. The manifest records source roots and external-file archive mappings. Never publish bootstrap.json: it includes private database/provider configuration and Rails key material, because archive encryption was deliberately not requested.

2. Rebuild the environment

Provision a supported Linux host and matching Ruby, Redmine/Rails, PostgreSQL client/server and application dependencies using the captured application/Gemfile.lock. Review the captured version metadata. Provision Redmine’s service account, private directories, external dependencies and database role. Recreate role privileges deliberately; this is a single-database dump, not a whole-cluster/global-role backup.

Restore the application archive into private staging, not directly over an operating installation. Inspect archive member names, symlinks and external_roots before extraction. application/ maps to the Redmine root, attachments/ maps to its attachment storage, and each external/N/ maps to the corresponding external root in the manifest. Restore external state/configuration/service files to reviewed locations with appropriate ownership and modes. Preserve Rails secret/key material and SMTP private state together; without matching keys, encrypted settings/grants cannot be decrypted.

Install the backup plugin from this repository if its files were not already captured, and install the locked application dependencies. Keep the worker stopped.

3. Restore the database

Create an empty, correctly encoded database owned by the intended Redmine role. Configure authentication without exposing passwords on command lines. After reviewing the dump and role mapping, restore it using pg_restore --exit-on-error --no-owner --role=REVIEWED_REDMINE_ROLE --dbname=NEW_DATABASE database.dump with suitable connection parameters/environment. Do not restore over a running production database. Check every restore error and application compatibility before running any required Redmine migrations.

Use the captured resolved database configuration only as a private reference; update the restored Redmine configuration for the replacement host. Existing Redmine plugin settings will be restored by the database dump. The private bootstrap is available if configuration must be reconstructed outside a working Redmine instance; it is not automatically imported by an unauthenticated endpoint.

4. Force Recovery Mode before starting

Set REDMINE_BACKUP_RECOVERY=1 in the replacement Redmine and worker environments. Alternatively place a file named RECOVERY inside the private backup directory’s control/ folder. A different host identity also triggers Recovery Mode, but explicit recovery protection should always be used for test/cloned hosts.

Reconstruct the private plugin control directory from the verified bootstrap using the standalone helper after restoring the same Rails secret and installing the application dependencies:

bundle exec ruby plugins/redmine_backup_plugin/bin/redmine-backup-bootstrap \
  /private/staging/bootstrap.json /private/new-backup-store

The destination must be empty with a writable existing parent. This restores encrypted metadata, grants and audit/history with a mandatory Recovery marker. Historical local payloads are marked unavailable because old backup directories are not recursively included in each new backup. Pending jobs are cleared. Review the generated private restored-plugin-settings.json, including paths and recipients, and import its non-secret settings through an explicitly controlled Rails maintenance session:

RAILS_ENV=production bundle exec rails runner \
  'Setting.plugin_redmine_backup_plugin = JSON.parse(File.read(ARGV.fetch(0)))' \
  /private/new-backup-store/restored-plugin-settings.json

Keep the worker stopped during this operation. The restored Rails key must match the key in the private bootstrap. Reconnect cloud grants if they have expired or rotated since capture. Do not accidentally create a second active installation managing the old remote namespace.

Start only the web service first. Check administrator login, issue/project data, attachments, themes/plugins, configuration and existing SMTP integration. Inspect the Backups dashboard. Confirm scheduling, cleanup and operational email remain blocked in Recovery Mode. Gateway/HTTPS infrastructure is excluded from this backup and must be provisioned separately.

5. Activate deliberately

Fence the old server so it cannot resume jobs. Remove the recovery environment override, then use Activate This Restored Instance. The schedule remains paused. Review storage destinations, recipient selections, keys, retention and source coverage; ensure paths fit the replacement host. Run an isolated backup/upload verification and test notification when appropriate, then enable scheduling.

Record the actual restore time, errors, recovery point and validation results. Checksum verification alone is not a successful restoration drill.

Security and operational limits

  • Backup administration requires a Redmine administrator. Rails authenticates users and protects POST actions against CSRF. Provider OAuth uses one-use state, expiry, destination binding and S256 PKCE. No SMTP application permissions are reused for storage.

  • Secrets are write-only in the UI and encrypted in mode-0600 control files within mode-0700 local storage. No raw subprocess/provider errors or credentials are logged. Do not serve that directory through nginx/Apache/static aliases. Filesystem paths are administrator-only information.

  • Archive encryption is disabled by policy. Dumps, environment files and the private bootstrap can contain credentials/customer data. HTTPS/SSH transport verification remains required. Limit storage access appropriately.

  • The plugin performs no privilege escalation. External secrets or service environment files must be readable by the Redmine account; unreadable required coverage fails capture. Existing Redmine-specific file/directory environment variables and readable Redmine systemd units are discovered, and additional paths are configurable.

  • PostgreSQL capture inspection uses an explicit repeatable-read, read-only transaction. A database snapshot covers the dump and referenced attachment inventory, not an atomic whole-filesystem snapshot. Referenced attachments are hash/size checked while copied; changes to other copied files fail when detected. Long snapshots may delay vacuum cleanup and should be monitored operationally.

  • Only one writer process is allowed per shared local control directory. Do not use an unreliable network filesystem for control locks or deploy multiple independent stores against one namespace. The worker has a kernel lock and heartbeat; it does not permit unsafe automatic takeover of a still-running hung process.

  • df checks reserve before capture and during streaming. Unpredictable compression ratios, concurrent writers and platform behavior still require a restore/space drill. Use the service template’s CPU/I/O priority and configure sufficient disk capacity.

  • Retention checks installation/run ownership and reference namespaces. It never synchronizes a whole bucket or folder. Completion markers are removed before deleting eligible payloads so partial deletion cannot remain advertised as complete. Interrupted deletes may leave orphaned objects; these are not blindly swept. Duplicate completion markers are preserved rather than risking shared-payload deletion.

  • S3 Object Lock can be irreversible until expiry. The plugin checks existing capability and requests opt-in protection; it does not enable bucket policies, grant permissions or bypass holds. Versioning does not imply immutable protection. Old versions/provider recycle bins can outlive the configured successful-date count.

  • Provider credentials/grants can be revoked and rates/quotas vary. No provider integration is claimed as production-certified by unit mocks. Personal OneDrive uses delegated identity; business/SharePoint application access requires explicit drive/site addressing. Shared Drive and SharePoint policies require separate testing. New application private keys and device codes remain encrypted; managed-identity metadata requests are restricted to local/link-local endpoints and bypass proxies.

  • Alerts use existing Redmine delivery. Neither a dead server nor a stopped worker can send immediate native alerts; startup catch-up resumes after availability. Supervisors/organizational monitoring remain external operational responsibilities.

  • Recovery Mode is triggered by a different host identity, an explicit control/RECOVERY marker or REDMINE_BACKUP_RECOVERY=1. Identical VM clones may share identity, so restoration instructions require an explicit recovery flag. The plugin does not automatically restore a database or expose public backup download endpoints.

Deliberate initial boundaries

  • PostgreSQL and Linux are the supported capture environment. Unit tests can run on Windows; a Windows production worker is not supported.

  • Additional Ruby-capable providers are cataloged, not implemented adapters. Shared Drive and SharePoint authorization require actual tenant/account permissions and live compatibility tests. Google limited-input device flow and native-app callbacks are not applicable to this web plugin; legacy browser access tokens are supported through explicit expiring-token import.

  • No public download or automatic production-restore endpoint. Restoration remains an administrator-controlled offline process. The helper reconstructs control state and emits reviewed non-secret settings for an explicit Rails maintenance import.

  • Previously captured full backup directories are excluded from each new full backup. Bootstrap preserves their history as historical/unavailable when restored; it does not pretend their old local payloads exist.

  • Native alerts cannot report immediately while Redmine/worker/server is down. Recovery confirmations and scheduled daily-success emails are optional/off by default. Manually pinned recovery points remain a future enhancement.

  • Locked cleanup, duplicate markers, orphaned partial uploads and provider old versions may exceed retention counts. No blind remote orphan sweeping or forced hold removal occurs.

  • A started pg_dump is terminated on timeout/disk-check failure. Cloud requests have bounded per-request timeouts/retries. No global hard upload-duration limit is imposed across a large multipart upload; supervisor cancellation leaves resumable state.

  • Filesystem control locks require a reliable shared local filesystem. No multi-host distributed locking or unsafe hung-worker takeover is claimed.

  • Run/audit records contain safe status/identity metadata, not raw provider error bodies. Captured private bootstrap/configuration is intentionally sensitive and must remain private.

Deployment and release operations

This plugin runs inside Redmine; its background worker is a separate native Ruby process. Configuration, credentials and backup payloads belong to the installed instance and are never checked into the public source repository.

Installation sequence

  1. Inspect the current Redmine/Ruby/PostgreSQL versions, service account, environment-file paths, attachment root and existing dependency lockfile. The reusable tools/deployment_preflight.rb performs database diagnostics in an explicit read-only transaction.

  2. Package only source-controlled runtime, documentation and template files. Exclude .git, target, local runtimes, dependency caches, temporary captures and operator records. Keep a short-lived rollback copy of the existing Gemfile.lock until installation verification succeeds.

  3. Install into REDMINE_ROOT/plugins/redmine_backup_plugin as the Redmine service account. Run bundle install using the current Redmine environment. Compare the lockfile and avoid unrelated dependency upgrades. There are no plugin table migrations.

  4. Install the reviewed worker unit with the same service account, working directory, Ruby/Bundler and environment inputs as Redmine. Give the discovered local store private permissions. Restart Redmine and start the worker.

  5. Verify the plugin registry, routes, public login response, administrator page, worker heartbeat, private control files, queue and setup checks. Existing SMTP functionality and the gateway remain outside the deployment change.

  6. Initial storage is unconnected and backup scheduling is disabled. Select a destination, complete its authorization, choose recipients/retention, run the health check and validate a manual backup before enabling daily scheduling. No operational test email or cloud upload is sent just by loading the plugin.

The recovery worksheet is a private template for the actual host/service paths, checks and evidence. Live instance addresses, credentials, provider grants, service environment values and deployment archives are not part of the public documentation.

Rollback

If boot/dependency verification fails, stop the backup worker, remove only the newly installed plugin directory, restore the saved lockfile and restart Redmine with its original dependencies. Preserve any actual captured backup/control data separately. Do not drop Redmine tables or remove existing plugins. Remove the short-lived rollback lockfile and source upload after a verified installation.

Repository identity and history

Use the intended GitHub account for authentication and its verified/noreply address for commit attribution; these are separate settings. A deliberate replacement of published history must use an explicitly expected remote SHA with force-with-lease, so a collaborator’s intervening push is not overwritten.

Rewriting a branch removes its old commits from that branch’s history. It does not guarantee immediate erasure of GitHub caches, forks, clones or historical workflow references. Secrets must not be committed in the first place; credentials exposed elsewhere require their own remediation.

Public visibility permits reading/cloning/forking and proposing pull requests. Direct pushes still require authorized write access. Repository owners can additionally apply branch/ruleset protection.
